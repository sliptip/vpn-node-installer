# vpn-node-installer

Интерактивный установщик нового VPN-узла на чистой **Ubuntu 24.04 LTS x64**.

Текущие версии установщика и client helper: **0.2.0-dev**.

Новые узлы используют **VLESS → XHTTP stream-one → HTTP/3 (QUIC)**. TLS завершается на Nginx, до Xray запрос передаётся по локальному HTTP/2. Старый WebSocket inbound при новой установке не создаётся.

**Проверено локально 21.10.2026:** настоящий бинарник 3x-ui **v3.10.2** прошёл проверку логина/сессии, создание XHTTP inbound, чтение клиента и массовое создание клиентов через API. Шаблоны установщика проверены настоящими **Xray 26.10.10** и **Nginx 1.30.6**: VLESS передал HTTP-запрос через QUIC, журнал Nginx подтвердил `HTTP/3.0 200`. Пройдены регрессионные тесты и проверки Bash/ShellCheck.

**Проверено на VPS 21.10.2026:** оператор подтвердил успешную установку **0.2.0-dev** и работу внешнего подключения **VLESS/XHTTP/H3** с **3x-ui v3.10.2**. Проверка на реальном сервере завершена успешно; сообщение о неподтверждённой VPS-установке снято. История предыдущей проверки `0.1.8-dev` / `v3.8.5` от 16.09.2026 сохранена в CHANGELOG.md.

## 3x-ui: основной, проверенный и резервный релизы

Официальный upstream: https://github.com/MHSanaei/3x-ui.

- `XUI_PREFERRED="v3.10.2"` — основной кандидат, последний stable при подготовке изменения 21.10.2026; выпущен 14.10.2026, содержит Xray `26.10.10`.
- `XUI_KNOWN_GOOD="v3.8.5"` — ранее проверенная версия панели с прежним установщиком, сохранённая в выборе и цепочке отката. Последняя подтверждённая VPS-проверка новой H3-установки — `v3.10.2`.
- `XUI_FALLBACK_TAG="v3.8.0"` — аварийная версия; её зеркало `sliptip/3x-ui` и закреплённый SHA-256 сохраняются. Новые релизы в зеркало не архивируются.

При каждом запуске проверяется latest stable. Если он новее `v3.10.2`, предлагается он; если проверка недоступна или сообщает более старую версию — `v3.10.2`. Prerelease/dev теги не принимаются. Меню позволяет выбрать:

```text
1) Установить основной/latest релиз (по умолчанию)
2) Установить ранее проверенную v3.8.5
```

При неудаче установки или compatibility gate порядок попыток: выбранный upstream → `v3.8.5` upstream, если ещё не пытались → `v3.8.0` upstream → `v3.8.0` mirror. Каждая попытка использует installer из точного тега. Для зеркала проверяется закреплённый SHA-256 `236b837627520f0c4ae4134dc6a34ea5e294b69e158879795fe8cd51c5f3582c`.

Compatibility gate проверяет localhost-панель, точное совпадение логина в БД, настоящий вход с cookies/CSRF, сессию, API token, создание XHTTP inbound, listener `127.0.0.1:10001`, параметры транспорта, клиента и API helper. Перед следующей попыткой очищается только неудачная fresh-install установка.

После настройки Nginx отдельно выполняется настоящий локальный H3-тест. Его ошибка останавливает установку; она не запускает переустановку панели. Успешная установка записывает фактический `XUI_VERSION` в state. Работающие серверы автоматически не обновляются, не понижаются и не переводятся на другой транспорт.

## Что собирает

```text
client → UDP/443, TLS + HTTP/3 → nginx → /client/api/v3 → HTTP/2 h2c → 127.0.0.1:10001 → Xray / VLESS
```

Панель:

```text
browser → https://domain/dashboard-<domain-name>/ → nginx Basic Auth → 127.0.0.1:<random-port> → 3x-ui
```

`<domain-name>` — имя непосредственно перед доменной зоной. Например:

- `vpn.orion.example` → `/dashboard-orion/`, inbound `orion`
- `edge.nimbus.example` → `/dashboard-nimbus/`, inbound `nimbus`
- `relay.cobalt.example` → `/dashboard-cobalt/`, inbound `cobalt`

## Зафиксированные правила

- Ubuntu 24.04 LTS x64.
- IPv6 выключается сразу, в runtime и после reboot.
- AAAA-записи для VPN-домена не используются.
- VLESS over XHTTP, режим `stream-one`, клиентский ALPN только `h3`.
- XHTTP path `/client/api/v3`, padding `100-1000`.
- Xray inbound `127.0.0.1:10001`; внутренний TLS выключен.
- Nginx stable устанавливается из официального apt-репозитория nginx.org с проверкой signing key fingerprint и модулей HTTP/3, HTTP/2 и sub_filter.
- Nginx запускает worker от `www-data`, подключает `sites-enabled`; для XHTTP используется `grpc_pass` к h2c upstream.
- 3x-ui слушает только `127.0.0.1` на случайном внутреннем порту.
- TLS завершается на nginx, внутри Xray `security=none`.
- Subscription server 3x-ui (`2096`) выключается.
- `trustedXForwardedFor = ["X-Real-IP"]` на XHTTP inbound.
- nginx выставляет `X-Real-IP` и `X-Forwarded-For`.
- Первый клиент называется `default@<полный-домен>`, например `default@vpn.orion.example`.
- UUID клиента генерирует сам установщик как корректный UUID v4, а не панель.
- Basic Auth user всегда `admin`; пароль спрашивается.
- Логин и пароль 3x-ui спрашиваются отдельно. Логин — 1–64 ASCII-символа: первая латинская буква или цифра, далее также разрешены `. _ @ + -`. Пробелы, кириллица и повреждённые байты отклоняются с повторным вводом; регистр сохраняется.
- Let's Encrypt выпускается через certbot webroot без email.
- UFW разрешает текущий SSH-порт, `80/tcp`, `443/tcp` и `443/udp`. UDP/443 также должен быть разрешён в firewall провайдера.
- Способ SSH-аутентификации установщик не меняет.
- 3x-ui upstream — официальный `MHSanaei/3x-ui`; текущая проверенная на VPS версия — `v3.10.2`; ранее проверенный вариант отката (`XUI_KNOWN_GOOD`) — `v3.8.5`; закреплённый fallback — `v3.8.0`; аварийный mirror этой резервной версии — `sliptip/3x-ui`.
- Секреты, UUID и VLESS-ссылка не пишутся в постоянный лог.
- Нейтральный favicon встроен в установщик и явно подключается как к сервисной странице, так и к HTML панели 3x-ui через nginx.

## Preflight

До развёртывания VPN проверяются Telegram, обычный IPv4 Internet, публичный IPv4 сервера, authoritative DNS и резолверы `1.1.1.1`, `8.8.8.8`, `9.9.9.9`. A-запись должна содержать ровно ожидаемый IPv4, AAAA должна отсутствовать в успешном ответе DNS. Авторитетные ответы должны иметь флаг `aa`.

DNS-запросы ограничены тайм-аутом. Недоступность сервера показывается как `UNAVAILABLE`, некорректная запись/ответ — как `BLOCKED`, подтверждённые A/AAAA — как `GOOD`. Тайм-аут не означает отсутствие AAAA и не вызывает ложное сообщение «Установка прервана».

Обычно требуются корректные ответы всех NS и всех публичных резолверов. Если часть авторитетных NS недоступна, но хотя бы один NS и все три публичных резолвера подтвердили нужную A и отсутствие AAAA, установщик предлагает попробовать выпуск сертификата с явным подтверждением `[y/N]`. Только `y`/`Y` разрешает продолжение; Let’s Encrypt всё равно выполняет свою проверку. Любой полученный неверный IP, AAAA, CNAME, ошибка DNS или неавторитетный ответ запрещает этот вариант. Если публичный резолвер недоступен, продолжение также не предлагается.

Между проверками выдерживается пауза 30 секунд. Счётчик учитывает фактическое время запросов и ожидания; после окна 10 минут предлагается продолжить ожидание либо выйти. При повторном запуске после остановки на этапе DNS уже установленные пакеты допустимы; найденная существующая/частичная конфигурация 3x-ui или нашего nginx по-прежнему блокирует перезапись.

## Финальные проверки

Установщик проверяет nginx/x-ui, отсутствие IPv6, внешние TCP 80/443 и UDP 443, localhost-only панель и Xray, отсутствие `2096`, `/health`, Basic Auth → HTTP 401, сертификат, Telegram и `certbot renew --dry-run --no-random-sleep-on-renew`.

Для проверки транспорта временный Xray-клиент подключается к локальному Nginx с проверкой сертификата по домену, `network=xhttp`, `mode=stream-one`, `alpn=["h3"]`. Через SOCKS → VLESS он запрашивает публичный `https://<домен>/health` и проверяет точное тело ответа. Переход на H2/TCP в этом тесте не разрешён. Временная конфигурация приватная, после проверки процесс и файлы удаляются. Запись Nginx может появиться позже закрытия потока, поэтому её задержка не считается сбоем.

Nginx сохраняет только протокол и HTTP-статус VPN-потоков в `/var/log/nginx/vpn-transport.log`, без URL, UUID и query. Внешний QUIC всё равно нужно проверить реальным H3-клиентом с другого устройства: локальный тест не подтверждает маршрут через провайдера.

В финале показывается готовая VLESS-ссылка клиента `default@<полный-домен>`. После этого установщик ставит helper-команду `/usr/local/sbin/vpn-clients` из `clients.sh` этого же репозитория и спрашивает:

```text
Добавить дополнительных клиентов сейчас? [y/N]:
```

Можно отказаться — основная установка уже завершена. Позже helper запускается командой:

```bash
sudo vpn-clients
```

Реальный клиентский тест остаётся обязательной последней проверкой.

## Запуск dev-версии

Для новой установки 0.2.0-dev на чистом Ubuntu 24.04 x64. Запуск из предварительно скачанного файла:

```bash
curl -fsSLO https://raw.githubusercontent.com/sliptip/vpn-node-installer/main/install.sh
chmod +x install.sh
sudo ./install.sh
```

## Массовое добавление клиентов

На новых узлах helper ставится автоматически в `/usr/local/sbin/vpn-clients`. Его можно запустить сразу из финала `install.sh` либо позже:

```bash
sudo vpn-clients
```

Если helper нужно получить вручную, исходный файл лежит рядом с установщиком:

```bash
curl -fsSLO https://raw.githubusercontent.com/sliptip/vpn-node-installer/main/clients.sh
chmod +x clients.sh
sudo ./clients.sh
```

Файл со списком на сервер загружать не нужно. После запуска просто вставьте **весь список одним сплошным блоком** в SSH-терминал. Скрипт ждёт начала вставки без ограничения по времени, а после первого полученного символа собирает весь поток, включая незавершённую последнюю строку. Через **1,5 секунды без новых символов** ввод считается законченным.

Завершающий перевод строки больше не нужен: последняя строка сохраняется даже без `Enter`. Никакая специальная точка, пустая строка или `Ctrl+D` также не нужны.

Пример:

```text
Вставьте весь список имён или email одним блоком, по одному на строку.

alice@legacy.example
bob.smith@other.example
mobile-01

Ввод завершён.
```

Скрипт читает домен, путь панели, транспорт и порты из `/etc/vpn-node-installer/state.env` и работает через локальный API 3x-ui. На новых узлах это XHTTP `127.0.0.1:10001`. Старые state без полей транспорта сохраняют WS `/client/api/v2`, порт `10000` и ALPN `http/1.1`. Перед записью helper сверяет state с фактическим inbound; несовпадение останавливает работу. Для вручную изменённых узлов нужен соответствующий state, автоматического угадывания нет.

Вставлять можно простые имена, полноценные email или одноколоночную Markdown-таблицу. Для email берётся только часть слева от первого `@`, поэтому, например:

```text
alice@legacy.example       → alice
bob.smith@other.example    → bob.smith
mobile-01                  → mobile-01
```

После нормализации клиент получает имя вида `alice@vpn.orion.example`, то есть исходный почтовый домен не переносится на VPN-узел. Пустые строки и Markdown-разделители игнорируются, `\@` понимается как обычный `@`, повторы после нормализации удаляются. Имя обязано содержать хотя бы одну латинскую букву или цифру, поэтому строки вроде `.`, `..`, `_`, `+` или `-` отклоняются до любых изменений на сервере.

Перед изменениями показывается предпросмотр и запрашивается **безопасное подтверждение `[y/N]`**. Добавление выполняется только после явного `y`/`Y`; простой `Enter` отменяет изменение. Уже существующие `name@<домен-узла>` не перезаписываются. Перед массовым созданием делается root-only SQLite backup в `/etc/vpn-node-installer/backups/`. UUID v4 генерируется отдельно для каждого нового клиента, после записи каждый созданный клиент перепроверяется через API.

Самый последний блок вывода содержит только готовые VLESS URL — по одной ссылке на строку, без отдельных подписей между ними.

## Повторный запуск

После успешной установки создаётся root-only state в `/etc/vpn-node-installer/`. Повторный запуск ничего не перезаписывает и предлагает только безопасную диагностику либо выход.

Если обнаружена чужая/частичная установка nginx/3x-ui без нашего маркера, скрипт останавливается.

## Лог

```text
/var/log/vpn-node-installer.log
```

Пароли, API token, UUID клиента и VLESS-ссылка туда не записываются. `clients.sh` также не пишет созданные UUID/VLESS URL в постоянный лог.

Файл upstream `/etc/x-ui/install-result.env` содержит открытые учётные данные. Наш установщик использует его API token во время настройки, а после успешного прохождения compatibility gate намеренно удаляет файл. Его отсутствие после завершения установки ожидаемо.

Сам upstream installer пока выводит пароль и API token в терминал; это отдельный известный недостаток. Проверка входа `0.1.7-dev` не печатает пароль, cookies или тела HTTP-ответов и не сохраняет их в файлы.

## Автопроверка репозитория

`.github/workflows/validate.yml` проверяет `install.sh`, включая invariants для known-good/fallback/compatibility gate, резервного `sliptip/3x-ui` и сохранения собственной версии установщика. Также запускаются локальные regression-тесты `tests/`: DNS-тайм-ауты и противоречивые ответы, явное разрешение продолжения, выбор версий и порядок fallback, повреждённый логин, отказ входа, CSRF/cookies, проверка сессии и запрет передачи пароля по редиректу. Тесты используют временную SQLite и локальный HTTP-стенд, не изменяют серверы. Отдельный `.github/workflows/validate-clients.yml` проверяет Bash-синтаксис и ShellCheck для `clients.sh`, запускает встроенный self-test нормализации и проверяет fail-safe `[y/N]` подтверждение.

Для запуска локального теста с настоящими бинарниками (не устанавливает сервисы):

```bash
XRAY_BINARY=/absolute/path/to/xray-linux-amd64 \
NGINX_BINARY=/absolute/path/to/nginx \
python3 -m unittest discover -s tests -v
```

CI отдельно скачивает закреплённые по SHA-256 бинарники и запускает этот QUIC-тест. Без этих переменных при ручном запуске интеграционный QUIC-тест пропускается, остальные тесты работают офлайн. Стенд использует временные файлы, тестовый сертификат и свободные локальные порты. Только в стендовом outbound разрешён конкретный loopback-порт HTTP-цели: production-конфигурация сохраняет стандартную защиту Xray от доступа к приватным адресам.
