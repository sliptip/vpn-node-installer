# vpn-node-installer

Интерактивный установщик нового VPN-узла на чистой **Ubuntu 24.04 LTS x64**.

Текущая версия: **0.1.6-dev**.

Базовая `0.1.0-dev` уже прошла первый полный end-to-end тест на чистом VPS: установка завершилась штатно, панель открылась, а созданная VLESS-конфигурация успешно подключилась реальным клиентом. `0.1.1-dev` добавила найденные после этого теста исправления, `0.1.2-dev` — массовый client helper и его запуск из финала первичной установки, `0.1.3-dev` — безопасный выбор версии 3x-ui и fresh-install fallback, `0.1.4-dev` — безопасное подтверждение массового добавления клиентов и корректное сохранение версии установщика, `0.1.5-dev` — резервный known-good источник `sliptip/3x-ui` на случай недоступности официального upstream, а `0.1.6-dev` — надёжный idle-ввод без завершающего Enter и защита от имён из одних знаков пунктуации. Ветка пока остаётся development-версией.

## 3x-ui: источник, known-good и новые версии

3x-ui берётся из официального upstream-репозитория:

- https://github.com/MHSanaei/3x-ui
- проверенная база совместимости проекта: **3x-ui v3.8.0**

Именно с `v3.8.0` был выполнен первый успешный clean-VPS end-to-end прогон 15.09.2026, включая создание inbound, открытие панели и реальное VLESS-подключение клиента. Поэтому `v3.8.0` сейчас является **last known good**.

При новой установке `install.sh` проверяет текущий latest stable upstream. Если latest совпадает с known-good, устанавливается `v3.8.0` без дополнительного вопроса. Если появился более новый stable-релиз, установщик предлагает:

```text
1) Попробовать новую stable-версию; при несовместимости автоматически вернуться на v3.8.0
2) Сразу установить проверенную v3.8.0 (по умолчанию)
```

Простой `Enter` выбирает безопасный вариант 2. Если latest определить не удалось, также используется `v3.8.0`.

Для known-good `v3.8.0` есть независимая резервная копия в `https://github.com/sliptip/3x-ui`: тот же tag/commit и архивированный amd64 release asset. Установщик всегда сначала пробует официальный `MHSanaei/3x-ui`; если fresh-install попытка known-good из официального источника не удаётся, состояние этой попытки очищается и `v3.8.0` повторяется из `sliptip/3x-ui`. Перед mirror-установкой проверяется сохранённый SHA-256 `236b837627520f0c4ae4134dc6a34ea5e294b69e158879795fe8cd51c5f3582c`.

Каждая попытка воспроизводима: installer script берётся **из тега выбранного релиза**, и этому же upstream installer передаётся тот же tag. То есть попытка `v3.9.0` не использует плавающий `main`, а fallback действительно ставит tagged `v3.8.0`.

Новая версия считается совместимой не только по `systemctl active`. До продолжения установки проверяются localhost-настройки панели, получение API token, создание требуемого VLESS inbound, запуск Xray на `127.0.0.1:10000`, наличие созданного клиента и рабочие API, используемые нашим client helper. Если candidate не проходит этот compatibility gate, его fresh-install состояние удаляется и выполняется чистая установка known-good `v3.8.0`.

Автоматический fallback разрешён **только во время первичной установки на чистом узле**. Уже работающие серверы установщик автоматически не обновляет и не понижает в версии. Успешная пробная установка нового stable-релиза на одном VPS также сама по себе не меняет глобальный known-good: он обновляется в проекте только после отдельного тестирования.

Фактически установленный tag записывается в `/etc/vpn-node-installer/state.env` как `XUI_VERSION` и показывается в итоговом summary.

## Что собирает

```text
client → domain:443 → nginx (TLS) → /client/api/v2 → 127.0.0.1:10000 → Xray / VLESS / WebSocket
```

Панель:

```text
browser → https://domain/dashboard-<domain-name>/ → nginx Basic Auth → 127.0.0.1:<random-port> → 3x-ui
```

`<domain-name>` — имя непосредственно перед доменной зоной. Например:

- `vpn.orion.example` → `/dashboard-orion/`, inbound `orion`
- `edge.nimbus.example` → `/dashboard-nimbus/`, inbound `nimbus`
- `relay.cobalt.example` → `/dashboard-cobalt/`, inbound `cobalt`

## Зафиксированные правила

- Ubuntu 24.04 LTS x64.
- IPv6 выключается сразу, в runtime и после reboot.
- AAAA-записи для VPN-домена не используются.
- VLESS over WebSocket.
- WebSocket path всегда `/client/api/v2`.
- Xray inbound всегда `127.0.0.1:10000`.
- 3x-ui слушает только `127.0.0.1` на случайном внутреннем порту.
- TLS завершается на nginx, внутри Xray `security=none`.
- Subscription server 3x-ui (`2096`) выключается.
- `trustedXForwardedFor = ["X-Real-IP"]` на WS inbound.
- nginx выставляет `X-Real-IP` и `X-Forwarded-For`.
- Первый клиент называется `default@<полный-домен>`, например `default@vpn.orion.example`.
- UUID клиента генерирует сам установщик как корректный UUID v4, а не панель.
- Basic Auth user всегда `admin`; пароль спрашивается.
- Логин и пароль 3x-ui спрашиваются отдельно.
- Let's Encrypt выпускается через certbot webroot без email.
- UFW разрешает текущий SSH-порт, `80/tcp` и `443/tcp`.
- Способ SSH-аутентификации установщик не меняет.
- 3x-ui upstream — официальный `MHSanaei/3x-ui`; current known-good — `v3.8.0`; аварийный mirror known-good — `sliptip/3x-ui`.
- Секреты, UUID и VLESS-ссылка не пишутся в постоянный лог.
- Нейтральный favicon встроен в установщик и явно подключается как к сервисной странице, так и к HTML панели 3x-ui через nginx.

## Preflight

До развёртывания VPN проверяются Telegram, обычный IPv4 Internet, публичный IPv4 сервера, authoritative DNS и резолверы `1.1.1.1`, `8.8.8.8`, `9.9.9.9`. A-запись должна указывать только на текущий IPv4, AAAA должна отсутствовать.

Если публичные DNS ещё держат старый кэш, установщик ждёт по 30 секунд до 10 минут, после чего позволяет продолжить ожидание или — только когда authoritative DNS уже корректны — попробовать выпуск сертификата.

## Финальные проверки

Установщик проверяет nginx/x-ui, отсутствие IPv6, внешние `80/443`, localhost-only панель и Xray, отсутствие `2096`, `/health`, Basic Auth → HTTP 401, WebSocket handshake → HTTP 101, сертификат, Telegram после установки и `certbot renew --dry-run`.

WebSocket-проверка намеренно глушит ожидаемый timeout после уже полученного `101`, чтобы успешный handshake не выглядел как ошибка `curl (28)`.

В финале показывается готовая VLESS-ссылка клиента `default@<полный-домен>`. После этого установщик ставит helper-команду `/usr/local/sbin/vpn-clients` из `clients.sh` этого же репозитория и спрашивает:

```text
Добавить дополнительных клиентов сейчас? [y/N]:
```

Можно отказаться — основная установка уже завершена. Позже helper запускается командой:

```bash
sudo vpn-clients
```

Реальный клиентский тест остаётся обязательной последней проверкой.

## Запуск dev-версии

Пока `0.1.6-dev` не прошла отдельный чистый VPS-прогон новой логики выбора/fallback 3x-ui вместе с последними safety-fix, лучше сначала скачать скрипт и просмотреть его, а не запускать через `curl | bash`.

```bash
curl -fsSLO https://raw.githubusercontent.com/sliptip/vpn-node-installer/main/install.sh
chmod +x install.sh
sudo ./install.sh
```

## Массовое добавление клиентов

На новых узлах helper ставится автоматически в `/usr/local/sbin/vpn-clients`. Его можно запустить сразу из финала `install.sh` либо позже:

```bash
sudo vpn-clients
```

Если helper нужно получить вручную, исходный файл лежит рядом с установщиком:

```bash
curl -fsSLO https://raw.githubusercontent.com/sliptip/vpn-node-installer/main/clients.sh
chmod +x clients.sh
sudo ./clients.sh
```

Файл со списком на сервер загружать не нужно. После запуска просто вставьте **весь список одним сплошным блоком** в SSH-терминал. Скрипт ждёт начала вставки без ограничения по времени, а после первого полученного символа собирает весь поток, включая незавершённую последнюю строку. Через **1,5 секунды без новых символов** ввод считается законченным.

Завершающий перевод строки больше не нужен: последняя строка сохраняется даже без `Enter`. Никакая специальная точка, пустая строка или `Ctrl+D` также не нужны.

Пример:

```text
Вставьте весь список имён или email одним блоком, по одному на строку.

alice@legacy.example
bob.smith@other.example
mobile-01

Ввод завершён.
```

Скрипт сам читает домен, путь панели и внутренний порт из `/etc/vpn-node-installer/state.env`, находит VLESS inbound `127.0.0.1:10000` и работает через локальный API 3x-ui.

Вставлять можно простые имена, полноценные email или одноколоночную Markdown-таблицу. Для email берётся только часть слева от первого `@`, поэтому, например:

```text
alice@legacy.example       → alice
bob.smith@other.example    → bob.smith
mobile-01                  → mobile-01
```

После нормализации клиент получает имя вида `alice@vpn.orion.example`, то есть исходный почтовый домен не переносится на VPN-узел. Пустые строки и Markdown-разделители игнорируются, `\@` понимается как обычный `@`, повторы после нормализации удаляются. Имя обязано содержать хотя бы одну латинскую букву или цифру, поэтому строки вроде `.`, `..`, `_`, `+` или `-` отклоняются до любых изменений на сервере.

Перед изменениями показывается предпросмотр и запрашивается **безопасное подтверждение `[y/N]`**. Добавление выполняется только после явного `y`/`Y`; простой `Enter` отменяет изменение. Уже существующие `name@<домен-узла>` не перезаписываются. Перед массовым созданием делается root-only SQLite backup в `/etc/vpn-node-installer/backups/`. UUID v4 генерируется отдельно для каждого нового клиента, после записи каждый созданный клиент перепроверяется через API.

Самый последний блок вывода содержит только готовые VLESS URL — по одной ссылке на строку, без отдельных подписей между ними.

## Повторный запуск

После успешной установки создаётся root-only state в `/etc/vpn-node-installer/`. Повторный запуск ничего не перезаписывает и предлагает только безопасную диагностику либо выход.

Если обнаружена чужая/частичная установка nginx/3x-ui без нашего маркера, скрипт останавливается.

## Лог

```text
/var/log/vpn-node-installer.log
```

Пароли, API token, UUID клиента и VLESS-ссылка туда не записываются. `clients.sh` также не пишет созданные UUID/VLESS URL в постоянный лог.

## Автопроверка репозитория

`.github/workflows/validate.yml` проверяет `install.sh`, включая invariants для known-good/fallback/compatibility gate, резервного `sliptip/3x-ui` и сохранения собственной версии установщика. Отдельный `.github/workflows/validate-clients.yml` проверяет Bash-синтаксис и ShellCheck для `clients.sh`, запускает встроенный self-test нормализации и проверяет fail-safe `[y/N]` подтверждение.
